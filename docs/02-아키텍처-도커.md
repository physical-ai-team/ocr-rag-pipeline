# 아키텍처: Docker 컨테이너 구성

## Docker를 왜 쓰나 (처음 보는 사람용)

- **컨테이너** = 프로그램 + 그 프로그램이 돌아가는 데 필요한 환경(Python 버전, 라이브러리 등)을 통째로 담은 상자.
- 누구 PC에서 실행하든 상자 안 환경은 똑같다 → "내 PC에선 되는데?" 문제가 사라진다.
- **기능별로 나눈다** = OCR 상자, 임베딩 상자, DB 상자… 처럼 기능마다 따로 컨테이너를 만든다.
  - 한 기능이 죽어도 나머지는 산다.
  - 팀원별로 맡은 컨테이너만 작업하면 돼서 서로 충돌이 적다.
  - OCR처럼 무거운 라이브러리가 다른 기능의 환경을 오염시키지 않는다.
- **docker compose** = 여러 컨테이너를 한 번에 켜고 끄는 도구. `docker compose up` 한 줄로 전체 시스템이 뜬다.

> conda 가상환경(`environment.yml`)은 각자 PC에서 코드 작성·테스트할 때 쓰고,
> Docker는 전체 시스템을 합쳐서 실행할 때 쓴다고 생각하면 된다.

## 컨테이너 구성 (현재)

| 컨테이너 | 하는 일 | 담당 단계 | 기술 |
| --- | --- | --- | --- |
| `api` | QR 세션, 폰 프레임 수신(WebSocket), 저장 현황 푸시, RAG 검색, **빌드된 프론트 서빙** | 2, 3, 5 화면, 6 | FastAPI, Gemini |
| `pipeline` | 프레임 → OCR → 문장 분리 → 임베딩 → 중복 검사 → DB 저장, 질문 검색 | 4, 5 | EasyOCR, sentence-transformers |
| (컨테이너 없음) | VectorDB | 5, 6 | **Supabase** (클라우드 PostgreSQL + pgvector) |

처음엔 `ocr` / `embedding` / `vectordb` 를 따로 나누려 했지만 바꿨다.
- OCR 과 임베딩은 한 프레임을 이어서 처리하고 중복 검사도 같이 해서, 한 컨테이너(`pipeline`)로 묶는 게 단순하다.
- DB 는 Supabase(클라우드)를 써서 띄울 컨테이너가 없다.
- 프론트는 `npm run build` 결과를 api 가 서빙한다 (폰 테스트 때 터널 하나로 충분).

```
 휴대폰 ──JPEG(WebSocket)──▶ api ──JPEG(HTTP)──▶ pipeline ──문장+벡터──▶ Supabase
                              │ ◀──저장 결과──────┘     ▲
 대시보드 ◀──저장 현황(WS)─────┤                         │
 대시보드 ──질문──▶ api ──────────── /search ────────────┘
                     └──▶ Gemini 답변 ──▶ 대시보드
```

자세한 주소 규칙과 실행 방법은 [05-저장현황-RAG-도커.md](05-저장현황-RAG-도커.md).

## 폴더 구조

```
ocr-rag-pipeline/
├── src/, public/          # frontend
├── services/
│   ├── api/               # Dockerfile, app/, tests/
│   └── pipeline/          # Dockerfile, app/, tests/, sql/
├── docker-compose.yml     # 전체 컨테이너 정의
├── .env.example           # 필요한 키 목록 (.env 로 복사)
├── environment.yml        # 로컬 개발용 conda 환경
└── docs/
```

새 기능을 서비스로 추가할 때는 `services/<이름>/` 에 `Dockerfile` 과 `requirements.txt`(버전 `==` 고정)를 두고 `docker-compose.yml` 에 등록한다.
